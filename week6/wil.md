이번 6주차 수업에서는 백엔드 개발에서 특히 중요하지만 자주 간과되는 예외 처리 방식과 API 문서화 방법을 다뤘다.
실무에서 문제가 발생했을 때 단순히 서버가 죽거나 500 에러만 보내는 방식은 고객 경험을 망치기 때문에, 정확한 원인 안내·정확한 HTTP 상태 코드·일관된 응답 구조가 필요하다는 점을 배웠다.

먼저 “유효성 검사”의 중요성을 강조했다.
우리는 그동안 단순히 DTO를 통해 데이터를 받았지만, 클라이언트가 항상 정상적인 형식으로 요청을 보내리라는 보장은 없었다. 예를 들어 비밀번호 길이 제한이 존재한다고 하더라도, 클라이언트가 100자 이상의 문자열을 보낼 수 있다. 실제로 이런 상황이 발생하면 서버는 DB 에러를 터뜨리고 500 Internal Server Error가 발생한다.
이때 클라이언트는 “서버 오류네?”라고 생각하지만, 사실 잘못한 것은 클라이언트다.
이 경험을 통해 400 Bad Request를 통해 잘못된 요청임을 명확히 알려야 한다는 점을 이해했다.

이를 해결하기 위한 첫 단계는 DTO에 유효성 검사를 적용하는 것이다.
@NotNull, @Size, @Pattern 등을 활용하면 필드별로 제약을 명시할 수 있고, Controller에서 @Valid를 사용하면 요청 데이터가 DTO 조건을 만족하는지 자동으로 검증된다.
즉, 예외를 DB나 서비스 레이어에서 나중에 발견하는 것이 아니라, 가장 앞단인 Controller에서 걸러낸다는 점이 핵심이었다.
이 과정을 통해 API를 더 견고하게 만들 수 있다는 것을 느꼈다.

하지만 유효성 검사만으로는 충분하지 않았다.
서버는 여전히 여러 종류의 예외를 발생시키는데, 각 컨트롤러마다 try-catch를 반복하는 방식은 유지보수성이 매우 떨어진다.
이를 해결하기 위해 전역 예외 처리(Global Exception Handler) 개념을 배웠다.
스프링의 @ControllerAdvice를 사용하면 애플리케이션 전체에서 발생하는 예외를 한 곳에서 처리할 수 있다.
이 방식은 중복 코드를 없애고, 예외 처리 로직을 API의 공통 관심사로 분리하는 AOP 방식이라는 점이 인상 깊었다.
핵심은 “핵심 비즈니스 로직과 예외 대응 로직을 분리한다”는 것이다.

또한 단순히 예외를 메시지 문자열로 남발하지 않고, 에러 메시지를 상수로 관리하는 방식도 배웠다.
여러 코드에서 동일한 문자열을 반복해 사용하면 수정이 매우 어렵다.
따라서 message 패키지 안에 ErrorMessage 클래스를 두고, 오류 메시지를 상수로 정의하여 사용하는 방식이 유지보수에 훨씬 유리하다는 점을 깨달았다.

후반부에는 Swagger(OpenAPI) 를 이용해 API 문서화를 진행했다.
API는 혼자 사용하는 것이 아니라 프론트엔드, 다른 개발팀, 심지어 외부 사용자와의 협업에 필수적이기 때문에, 명확하고 접근하기 쉬운 문서가 필요하다.
Swagger는 백엔드 코드를 기반으로 UI 형태의 API 문서를 자동 생성해주기 때문에 실제 API 테스트까지 가능하다.
@Operation, @Tag, @ApiResponse 같은 어노테이션은 단순히 보기 좋게 만드는 것이 아니라, API의 의미와 데이터 흐름을 명확히 표현하는 역할을 한다는 점을 알게 되었다.
